## 思维框架

在编写 PRD 之前，先回答几个关键问题：

* **目标用户**：谁会使用这个产品？他们的背景、角色和痛点是什么？尽量具体，避免笼统的"所有人"。
* **核心问题**：产品要解决什么根本问题？描述用户在现实场景下遇到的难题，而不是解决方案本身。
* **核心价值**：为什么你的解决方案对目标用户有价值？和现有方案相比，在哪些方面更好或更方便？
* **成功指标**：如何衡量产品的成功？例如活跃用户数、转化率、完成任务的时间等可量化指标。

## MoSCoW 功能优先级框架

使用 MoSCoW 方法对所有功能进行分类，确保 MVP 聚焦在核心价值上。

### Must Have (必须有) - MVP 核心功能
**定义**: MVP 绝对不能缺少的功能，没有这些功能产品无法交付核心价值。

**判断标准**:
- 问自己："如果没有这个功能，产品还能工作吗？"
- 如果答案是"不能"，则是 Must Have
- 直接支持核心用户故事的完成路径

**示例**:
- 记账应用: "添加支出记录"、"查看支出列表"
- 待办事项: "创建任务"、"标记完成"
- 笔记应用: "创建笔记"、"编辑笔记"、"查看笔记列表"

**编写要求**:
- 每个 Must Have 功能必须有对应的用户故事
- 描述清晰的成功标准
- 不超过 5-7 个核心功能

### Should Have (应该有) - 重要但非阻塞
**定义**: 重要但不是关键路径的功能，可以在 v1.1 或 v1.2 实现。

**判断标准**:
- 用户会明显感受到缺失，但可以暂时用变通方案
- 对产品体验有明显提升
- 不影响核心价值传递

**示例**:
- 记账应用: "导出报表"、"分类统计"
- 待办事项: "设置提醒"、"任务分类"
- 笔记应用: "搜索功能"、"标签管理"

**编写要求**:
- 标注为"未来迭代"
- 说明为什么当前阶段可以延后

### Could Have (可以有) - 锦上添花
**定义**: 锦上添花的功能，资源充裕时实现。

**判断标准**:
- 不影响核心体验
- 用户不会特别注意到缺失
- 主要是为了提升满意度而非解决问题

**示例**:
- 记账应用: "预算提醒"、"多币种支持"
- 待办事项: "自定义主题"、"快捷键"
- 笔记应用: "Markdown 预览"、"代码高亮"

**编写要求**:
- 列在"非目标 (Out of Scope)"部分
- 简短说明可能的实现时机

### Won't Have (不会有) - 明确排除
**定义**: 明确排除的功能，防止范围蔓延。

**判断标准**:
- 与核心价值无关
- 技术复杂度高但价值低
- 需要额外的基础设施或依赖

**示例**:
- 记账应用: "社交分享"、"投资建议"
- 待办事项: "团队协作"、"视频会议"
- 笔记应用: "实时协作"、"版本控制"

**编写要求**:
- 必须列在 PRD 的"非目标"部分
- 说明为什么排除（而不仅仅是"不做"）

## 用户故事编写指南

使用标准的用户故事格式描述功能：

**模板**:
```
作为 [角色/用户类型]
我想要 [功能/操作]
以便 [业务价值/目标]
```

**Must Have 示例**:
```
作为一个预算意识强的用户
我想要记录每一笔支出
以便了解我的消费去向和控制预算

验收标准:
- 可以输入支出金额和描述
- 可以选择支出类别
- 记录立即显示在支出列表中
- 显示当前日期和时间
```

**Should Have 示例**:
```
作为一个定期需要报税的用户
我想要导出月度支出报表
以便提交给会计或税务部门

验收标准:
- 可以选择时间范围
- 导出为 CSV 或 PDF 格式
- 包含所有支出细节
```

## PRD 文档结构要求

生成的 `prd.md` 必须包含以下章节：

### 1. 概述
```markdown
# 产品需求文档

## 产品概述
[1-2 句话描述产品的主要目的和形式]

## 背景和目标
[为什么需要这个产品？要解决什么问题？]
```

### 2. 目标用户画像
```markdown
## 目标用户

### 主要用户群体
- **角色**: [职业/身份]
- **年龄**: [范围]
- **技术能力**: [初级/中级/高级]
- **使用场景**: [何时何地使用]
- **痛点**: [当前遇到的具体问题]

### 次要用户群体
[如果有，简要描述]
```

### 3. 核心价值主张
```markdown
## 核心价值

**解决的问题**: [用户当前的痛点]

**我们的方案**: [产品如何解决这个问题]

**差异化优势**:
- [相比竞品或现有方案的优势 1]
- [优势 2]
- [优势 3]
```

### 4. 功能需求 (MoSCoW 分类)
```markdown
## 功能需求

### Must Have (MVP 必须功能)

#### 1. [功能名称]
**用户故事**:
作为 [角色]
我想要 [功能]
以便 [价值]

**验收标准**:
- [ ] [具体可验证的标准 1]
- [ ] [标准 2]
- [ ] [标准 3]

#### 2. [功能名称]
...

### Should Have (未来迭代)
- [功能名称]: [简要说明]
- [功能名称]: [简要说明]

### Could Have (锦上添花)
- [功能名称]
- [功能名称]
```

### 5. 用户流程
```markdown
## 核心用户流程

### 主流程: [流程名称]
1. 用户 [操作 1]
2. 系统 [响应 1]
3. 用户 [操作 2]
4. 系统 [响应 2]
5. 流程完成

**预期结果**: [用户达成的目标]
```

### 6. 非目标 (Won't Have)
```markdown
## 非目标 (Out of Scope)

当前阶段明确不包含的功能：

- **[功能名称]**: [为什么不做]
- **[功能名称]**: [为什么不做]
- **[功能名称]**: [可能的未来规划]
```

### 7. 成功指标
```markdown
## 成功指标

**产品目标**:
- [可量化的目标 1]
- [可量化的目标 2]

**关键指标 (KPIs)**:
- 用户留存率: [目标值]
- 核心功能使用率: [目标值]
- 任务完成时间: [目标值]

**验证方法**:
[如何收集和验证这些指标]
```

### 8. 假设和风险
```markdown
## 假设

**市场假设**:
- [关于市场的假设 1]
- [假设 2]

**用户行为假设**:
- [关于用户的假设 1]
- [假设 2]

**技术可行性假设**:
- [技术假设 1]
- [假设 2]

## 风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| [风险描述] | 高/中/低 | 高/中/低 | [如何应对] |
```

## 决策原则

* **以用户为中心**：任何功能的添加都必须直接对应目标用户的痛点和核心价值。
* **关注 MVP**：优先列出最小可行产品（MVP）范围，只包含完成关键任务所需的功能。超出这个范围的需求应作为未来迭代或非目标列出。
* **非目标明确**：在文档中清楚列出当前阶段不计划解决的问题和功能，避免范围蔓延。
* **可测试性**：每项功能描述应具体且可验证，后续团队能够据此编写测试用例。

## 质量检查清单

在完成 PRD 之前，确认以下各项：

### 用户和问题
- [ ] 目标用户描述具体（而非"所有人"）
- [ ] 核心问题清晰明确
- [ ] 价值主张差异化明显

### 功能范围
- [ ] Must Have 功能不超过 5-7 个
- [ ] 每个 Must Have 功能都有用户故事
- [ ] Should Have 和 Won't Have 明确列出
- [ ] 所有功能都通过 MoSCoW 分类

### 用户故事
- [ ] 使用标准格式 (作为...我想要...以便...)
- [ ] 包含可验证的验收标准
- [ ] 聚焦在用户价值而非实现细节

### 文档完整性
- [ ] 包含所有必需章节
- [ ] 成功指标可量化
- [ ] 假设和风险已识别
- [ ] 非目标明确列出

### 禁止项检查
- [ ] 没有技术实现细节
- [ ] 没有 UI 设计描述
- [ ] 没有模糊的用户描述
- [ ] 没有未经证实的功能堆砌

---

## 不要做 (NEVER)

* **NEVER** 在 PRD 中讨论技术实现、架构或 UI 布局；这些属于后续阶段；
* **NEVER** 使用模糊或泛泛而谈的用户描述；
* **NEVER** 在没有明确价值支撑的情况下堆砌功能；
* **NEVER** 忽略成功指标或假设，这会导致评估困难；
* **NEVER** 跳过 MoSCoW 分类，直接列功能清单；
* **NEVER** 将 Should Have 或 Could Have 功能混入 Must Have；
* **NEVER** 使用"可能"、"或许"等不确定的表达；
* **NEVER** 遗漏验收标准或使用不可验证的标准。

通过遵循上述思维框架和原则，你可以编写出简洁、有针对性的 PRD，为后续设计与开发奠定坚实基础。
