# 失败与回滚策略

本策略文档定义了在调度过程中如何识别失败、如何进行重试与回滚，以及何时需要人类介入。Sisyphus 必须在发现任何问题时引用并遵守此策略。

## 一、定义失败

以下任何情况均被视为 Stage 失败：

* **输出缺失**：`pipeline.yaml` 指定的输出文件不存在或命名不符；
* **不符合 exit_criteria**：输出内容未满足 `pipeline.yaml` 中该 Stage 的 `exit_criteria`；
* **越权写入**：Agent 向未授权的目录或文件写入内容；
* **其他异常**：例如脚本错误、无法读取输入等导致无法完成任务。

## 二、重试机制

* 每个 Stage 默认允许 **自动重试一次**。调度器应要求 Agent 在保持现有产物的基础上修正问题，而非完全重做；
* 若第二次尝试仍然失败，调度器必须暂停流水线并进入人工介入流程；
* 重试次数和逻辑可根据任务复杂度在未来进行配置，但不得无限重试。

## 三、回滚与存档

* 当某 Stage 被判定失败时，调度器需要将该 Stage 的所有输出文件移动到 `artifacts/_failed/<stage-id>/` 目录，以避免污染后续流程，并便于后续分析；
* 调度器应回滚到最近一个成功的检查点，从该 Stage 重新开始执行，以确保上下游产物一致。

## 四、人类介入

* 当同一 Stage 连续失败两次时，调度器必须暂停执行并报告失败原因。此时需要人类检查输入、配置或技能是否存在问题；
* 人类介入后，可以修改输入文件、调整技能或修改参数，再继续执行剩余流程；
* 调度器不得在未得到人类确认的情况下跳过失败阶段或修改输出。

遵循以上规则可以降低错误传播风险，确保流水线稳定性和可调试性。
