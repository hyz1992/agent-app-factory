# 失败与回滚策略

本策略文档定义了在调度过程中如何识别失败、如何进行重试与回滚，以及何时需要人类介入。Sisyphus 必须在发现任何问题时引用并遵守此策略。

## 一、定义失败

以下任何情况均被视为 Stage 失败：

* **输出缺失**：`pipeline.yaml` 指定的输出文件不存在或命名不符；
* **不符合 exit_criteria**：输出内容未满足 `pipeline.yaml` 中该 Stage 的 `exit_criteria`；
* **越权写入**：Agent 向未授权的目录或文件写入内容；
* **其他异常**：例如脚本错误、无法读取输入等导致无法完成任务。

## 二、重试机制

* 每个 Stage 默认允许 **自动重试一次**。调度器应要求 Agent 在保持现有产物的基础上修正问题，而非完全重做；
* 若第二次尝试仍然失败，调度器必须暂停流水线并进入人工介入流程；
* 重试次数和逻辑可根据任务复杂度在未来进行配置，但不得无限重试。

## 三、回滚与存档

* 当某 Stage 被判定失败时，调度器需要将该 Stage 的所有输出文件移动到 `artifacts/_failed/<stage-id>/` 目录，以避免污染后续流程，并便于后续分析；
* 调度器应回滚到最近一个成功的检查点，从该 Stage 重新开始执行，以确保上下游产物一致。

## 四、人类介入

* 当同一 Stage 连续失败两次时，调度器必须暂停执行并报告失败原因。此时需要人类检查输入、配置或技能是否存在问题；
* 人类介入后，可以修改输入文件、调整技能或修改参数，再继续执行剩余流程；
* 调度器不得在未得到人类确认的情况下跳过失败阶段或修改输出。

## 五、常见失败场景与处理方案

### 5.1 Bootstrap 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| 输出缺失 | `input/idea.md` 不存在 | Agent 未正确写入文件 | 重试，检查写入路径 |
| 内容不完整 | idea.md 缺少关键章节 | 用户输入信息不足 | 暂停，请求用户补充信息 |
| 格式错误 | 不符合模板结构 | Agent 未遵循模板 | 重试，强调模板要求 |

**处理流程**:
```
1. 检查 input/ 目录是否存在 → 不存在则创建
2. 重试一次，提示 Agent 使用正确的模板
3. 若仍失败，请求用户提供更详细的产品描述
```

### 5.2 PRD 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| 包含技术细节 | PRD 出现技术栈描述 | Agent 越界 | 重试，强调职责边界 |
| 功能过多 | Must Have > 7 个 | 范围蔓延 | 重试，要求精简到 MVP |
| 用户描述模糊 | "所有人"、"大部分用户" | 未具体化 | 重试，要求具体用户画像 |
| 缺少非目标 | Non-Goals 为空 | 未明确边界 | 重试，要求列出非目标 |

**处理流程**:
```
1. 验证 prd.md 不包含技术关键词 (React, API, 数据库等)
2. 验证 Must Have 功能数量 ≤ 7
3. 验证目标用户有具体画像
4. 重试时提供具体的修正要求
```

### 5.3 UI 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| 页面超限 | 页面数量 > 3 | 范围蔓延 | 重试，要求精简页面 |
| 预览无法打开 | HTML 文件损坏 | 生成错误 | 重试，检查 HTML 语法 |
| 使用 AI 风格 | Inter 字体 + 紫色渐变 | 未遵循审美指南 | 重试，要求选择鲜明审美 |
| Schema 无效 | YAML 解析失败 | 语法错误 | 重试，验证 YAML 语法 |

**处理流程**:
```
1. 统计 ui.schema.yaml 中的页面数量
2. 尝试在浏览器中打开 preview.web/index.html
3. 验证 YAML 语法: npx js-yaml ui.schema.yaml
4. 检查是否使用禁止的 AI 风格元素
```

### 5.4 Tech 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| Prisma 语法错误 | schema.prisma 无效 | 语法问题 | 重试，运行 prisma validate |
| 过度设计 | 引入微服务/缓存 | 违反 MVP 原则 | 重试，要求简化架构 |
| 数据模型过多 | 表数量 > 10 | 范围蔓延 | 重试，精简数据模型 |
| 缺少 API 定义 | tech.md 无端点列表 | 内容不完整 | 重试，要求补充 API |

**处理流程**:
```
1. 运行 npx prisma validate 验证 schema
2. 检查 tech.md 是否包含必要章节
3. 统计数据模型数量
4. 检查是否引入非必要复杂技术
```

### 5.5 Code 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| 依赖安装失败 | npm install 报错 | 包版本冲突 | 检查 package.json，更新版本 |
| TypeScript 错误 | tsc 编译失败 | 类型问题 | 修复类型错误，重试 |
| 缺少必要文件 | 目录结构不完整 | 生成遗漏 | 重试，检查文件清单 |
| 测试失败 | npm test 失败 | 代码逻辑错误 | 修复测试，重试 |
| API 无法启动 | 端口监听失败 | 配置问题 | 检查环境变量配置 |

**处理流程**:
```
1. 运行 npm install --dry-run 检查依赖
2. 运行 npx tsc --noEmit 检查类型
3. 对照文件清单检查目录结构
4. 运行 npm test 验证测试
5. 若以上全部通过，尝试启动服务
```

**常见依赖问题修复**:
```bash
# 版本冲突
rm -rf node_modules package-lock.json
npm install

# Prisma 版本不匹配
npm install @prisma/client@latest prisma@latest

# React Native 依赖问题
npx expo install --fix
```

### 5.6 Validation 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| 验证报告不完整 | report.md 章节缺失 | Agent 未完成 | 重试 |
| 严重问题过多 | 错误数 > 10 | Code 阶段质量差 | 回滚到 Code 阶段 |
| 安全问题 | 检测到硬编码密钥 | 安全违规 | 回滚，修复安全问题 |

**处理流程**:
```
1. 解析 report.md 确认所有章节存在
2. 统计严重问题数量
3. 若严重问题 > 10，建议回滚到 Code 阶段
4. 检查安全扫描结果
```

### 5.7 Preview 阶段失败

| 错误类型 | 症状 | 原因 | 处理方案 |
|---------|------|------|----------|
| README 不完整 | 缺少安装步骤 | 内容遗漏 | 重试，补充步骤 |
| Docker 构建失败 | Dockerfile 错误 | 配置问题 | 修复 Dockerfile |
| 部署配置缺失 | 无 docker-compose | 未生成 | 重试，要求生成配置 |

**处理流程**:
```
1. 检查 README.md 包含所有必要章节
2. 尝试 docker build 验证 Dockerfile
3. 检查部署配置文件是否存在
```

## 六、错误日志格式

失败时，调度器必须记录以下信息到 `pipeline/error.log`：

```
============================================
ERROR REPORT
============================================
Timestamp: 2026-01-25T10:30:00Z
Stage: code
Attempt: 2/2
Status: FAILED

Error Type: TypeScript Compilation Error
Error Message: Cannot find module '@prisma/client'

Stack Trace:
  at Object.<anonymous> (src/lib/prisma.ts:1:1)
  at Module._compile (node:internal/modules/cjs/loader:1198:14)

Exit Criteria Failed:
  - [ ] 后端可启动且无重大错误 (FAILED)
  - [x] 客户端可渲染并访问
  - [x] 未引入额外的认证或无关功能

Failed Artifacts Moved To:
  artifacts/_failed/code/attempt-2/

Recommended Action:
  1. 检查 package.json 是否包含 @prisma/client
  2. 运行 npx prisma generate 生成客户端
  3. 重试 Code 阶段

============================================
```

## 八、失败恢复检查清单

在人工介入修复问题后，恢复执行前必须确认：

### 环境检查
- [ ] Node.js 版本 >= 18
- [ ] npm 版本 >= 9
- [ ] 磁盘空间充足
- [ ] 网络连接正常 (npm 下载)

### 状态检查
- [ ] `pipeline/state.json` 状态正确
- [ ] 上游 Stage 产物完整
- [ ] 失败产物已归档到 `_failed/`

### 修复确认
- [ ] 失败原因已明确
- [ ] 修复方案已实施
- [ ] 相关配置已更新

### 恢复执行
- [ ] 从失败的 Stage 重新开始
- [ ] 监控执行日志
- [ ] 验证输出产物

## 九、最佳实践

1. **早期失败**: 尽早发现问题，避免在后续 Stage 浪费时间
2. **详细日志**: 记录足够的上下文信息，便于排查问题
3. **原子操作**: 每个 Stage 的输出应该是原子的，便于回滚
4. **保留证据**: 失败产物归档后再重试，便于对比分析
5. **渐进重试**: 重试时提供更具体的指导，而非简单重复

遵循以上规则可以降低错误传播风险，确保流水线稳定性和可调试性。
